| PC4 | 192.168.1.4 | SW2 Fa0/2 |

SW1 and SW2 were connected through their GigabitEthernet0/1 interfaces.

All four PCs were part of the same:

```text
192.168.1.0/24
```

network.

At the beginning of the exercise, the switches had empty dynamic MAC address tables and the PCs had empty ARP tables.

## Predicting the PC1 to PC3 Communication

Before running the simulation, I worked through what I expected to happen when PC1 pinged PC3.

Because PC1 initially did not know PC3's MAC address, it could not immediately send the ICMP traffic directly to PC3.

It first needed to use ARP to determine which MAC address belonged to:

```text
192.168.1.3
```

I predicted the process would occur approximately like this:

1. PC1 generates an ARP request for 192.168.1.3.
2. PC1 sends the ARP request using an Ethernet broadcast.
3. SW1 receives the frame and learns PC1's source MAC address on Fa0/1.
4. SW1 floods the broadcast out its other active ports.
5. PC2 receives the ARP request but ignores it because the requested IP address does not belong to PC2.
6. SW2 receives the broadcast through Gi0/1 and learns PC1's MAC address through that interface.
7. SW2 floods the ARP request toward PC3 and PC4.
8. PC4 ignores the request.
9. PC3 recognizes that the requested IP address belongs to it.
10. PC3 sends an ARP reply back toward PC1.
11. The switches learn additional source MAC addresses as frames pass through them.
12. After PC1 learns PC3's MAC address, the ICMP echo request can be sent to PC3.
13. PC3 sends an ICMP echo reply back to PC1.

## Observing the ARP Broadcast

I used Packet Tracer's Simulation Mode to verify what happened when PC1 attempted to communicate with PC3.

![Analyzing PC1 packet showing the broadcast MAC address](<analyzing PC1 packet showing broadcast mac address.png>)

*Inspecting the ARP request generated by PC1 in Packet Tracer Simulation Mode.*

The PDU information showed that the ARP request was placed inside an Ethernet frame with the destination MAC address:

```text
FFFF.FFFF.FFFF
```

This is the Ethernet broadcast MAC address.

The broadcast was necessary because PC1 knew PC3's IP address but did not yet know PC3's MAC address.

The ARP request was effectively asking:

**Which device owns 192.168.1.3?**

Because the destination was a broadcast, the switches forwarded the request throughout the LAN rather than sending it to only one destination.

## Switch MAC Address Learning

While forwarding the traffic, the switches examined the **source MAC address** of incoming Ethernet frames.

This is how a switch dynamically learns where devices are located.

For example, when SW1 received the ARP request from PC1 on Fa0/1, it could associate PC1's MAC address with:

```text
Fa0/1
```

When SW2 received the same frame from SW1, it learned that PC1's MAC address could be reached through:

```text
Gi0/1
```

The switches continued learning addresses as additional devices generated traffic.

This helped reinforce an important switching concept:

**Switches learn MAC addresses from the source MAC address of frames they receive.**

They do not learn an address simply because it appears as the destination of a frame.

## ARP Reply and Unicast Forwarding

PC3 received the ARP broadcast and recognized that the requested IP address belonged to it.

PC3 then generated an ARP reply containing its MAC address.

Unlike the original ARP request, the reply could be sent as a **unicast** because PC3 already knew PC1's MAC address from the original request.

As the reply traveled back toward PC1, the switches learned PC3's MAC address as well.

Once the switches had learned the necessary MAC addresses, they could forward frames directly out the appropriate ports instead of flooding them throughout the LAN.

## How the Switch Uses the MAC Address Table

The lab helped me understand the basic decision a switch makes when receiving an Ethernet frame.

### Known Unicast

If the destination MAC address is already in the MAC address table, the switch forwards the frame only through the associated interface.

### Unknown Unicast

If the destination MAC address is not known, the switch floods the frame out other interfaces in the VLAN.

### Broadcast

If the destination is:

```text
FFFF.FFFF.FFFF
```

the switch floods the frame out the appropriate interfaces because the frame is intended for all devices within the broadcast domain.

This behavior was visible during the ARP process.

## ARP Table vs. MAC Address Table

One of the most useful parts of this lab was seeing the difference between the ARP table on a host and the MAC address table on a switch.

### ARP Table

A host uses the ARP table to associate:

```text
IP address → MAC address
```

For example, PC1 learned which MAC address belonged to:

```text
192.168.1.3
```

### Switch MAC Address Table

A switch uses its MAC address table to associate:

```text
MAC address → switch interface
```

For example, SW1 can learn that a particular MAC address is reachable through:

```text
Fa0/1
```

or through the connection toward SW2:

```text
Gi0/1
```

The two tables solve different problems, but they work together to allow Ethernet communication across the LAN.

## ARP and ICMP

This lab also helped me better understand the relationship between ARP and ICMP.

When PC1 ran:

```text
ping 192.168.1.3
```

the ICMP echo request could not initially be sent as a normal Ethernet unicast because PC1 did not yet know PC3's MAC address.

ARP first resolved:

```text
192.168.1.3
```

to PC3's MAC address.

After that information was learned, the ICMP traffic could be carried inside Ethernet frames addressed directly to PC3.

Conceptually:

```text
PC1 wants to ping PC3
        ↓
PC1 knows PC3's IP address
        ↓
PC1 does not know PC3's MAC address
        ↓
ARP Request — Broadcast
        ↓
ARP Reply — MAC address learned
        ↓
ICMP Echo Request — Unicast
        ↓
ICMP Echo Reply — Unicast
```

## What I Learned

This lab helped me understand what actually happens at Layer 2 before two devices on the same LAN can communicate.

### Switches Learn From Source MAC Addresses

A switch learns where devices are located by examining the source MAC address of incoming Ethernet frames.

It stores that information in its MAC address table along with the interface where the frame was received.

### ARP Uses Broadcasts

When a host knows an IPv4 address but does not know the corresponding MAC address, it can send an ARP request using the Ethernet broadcast address:

```text
FFFF.FFFF.FFFF
```

### Broadcasts Are Flooded

Because an ARP request is a broadcast, switches forward it throughout the local broadcast domain.

Devices that do not own the requested IP address ignore the request.

### ARP Replies Can Be Unicast

Once the destination device receives the ARP request, it can reply directly to the requesting host using the source information contained in the original request.

### MAC Learning Changes Switch Behavior

When a switch does not know where a destination MAC address is located, it may need to flood traffic.

After learning the address, it can forward future unicast frames only through the required interface.

### ARP and MAC Tables Are Different

A PC's ARP table maps IP addresses to MAC addresses.

A switch's MAC address table maps MAC addresses to switch interfaces.

Understanding the difference helped me better visualize how Layer 2 and Layer 3 addressing work together.

### A Ping Involves More Than ICMP

Running a simple `ping` can trigger other network activity first.

In this lab, ARP had to resolve the destination MAC address before the first ICMP echo request could be delivered.

Using Simulation Mode made this process visible instead of treating the ping as a single action.
